## 3. 논의 흐름 (요약)

1. **유스케이스 정리**: 판매자 편(C님), 예매자 편(팀원). 기능·스펙 정의 전에 유스케이스 명세를 먼저 작성.
2. **26개 테이블 초안 설계**: 계정, 공연장, 공연, 예매·결제, 운영 전체를 한 번에 설계.
3. **팀원들이 테이블 수에 겁먹음** → 테이블을 줄이는 방안(15개 안)을 논의했으나 **보류**. 대신 **부 단위로 하나씩 설명**하는 방식으로 결정.
4. **공연장 범위 논의**: 공연장 하나로 시작하고 확장 가능하게 vs 여러 공연장. 결과는 **여러 공연장을 관리자가 만들고, 판매자가 고르는 방식**.
5. **팀원의 공연장·좌석 추상화 가이드를 검토**: 인터페이스·전략 패턴의 필요성에 의문을 제기하고, 결론은 아래 4번의 "추상화 범위"로 정리.
6. **부 단위 설계와 설명 문서 작성**: 부마다 질문 라운드(제 기본값을 두고 답을 받는 방식) → 확정 → 한글 명세 카드 + 관계도 + 마크다운 작성.
7. **개발 분담 정리, 프로젝트 생성 준비** (Initializr 설정 정리).

## 4. 확정된 핵심 결정

### 계정·인증 (1부)
- 예매자·판매자·관리자는 **완전히 다른 세 테이블**이고, 서로 중복 검사를 하지 않음. (겸임 금지가 아니라 각자 따로 만드는 구조)
- 로그인은 **이메일**.
- 본인인증(처음은 Mock, 이후 토스 등): 예매자 `ci_hash` 필수·유일(탈퇴 회원 제외, 탈퇴 시 비움), 판매자(대표·담당자 모두) 필수·사업체 안에서 유일. 판매자 이메일은 전역 유일 그대로 (이메일 1개 = 사업체 1개).
- 판매자 사업체 = 최고 권한(대표) 계정의 소속. 담당자는 **초대 링크(`seller_invitation`)**로 합류. 사업체 코드 방식은 쓰지 않음.
- 약관은 `terms` 테이블(DB), 동의 기록은 `user_terms_agreement`.
- 회원 삭제는 `deleted_at` 소프트 삭제. JPA `@SQLRestriction`을 **전역으로 걸지 않음** (예매 이력이 탈퇴 회원을 참조하기 때문). 탈퇴할 때 개인정보는 비식별 처리.
- URL 분리: `/admin/**`, `/seller/**`.
- **관리자 로그인** (2026-11-12): `POST /api/v1/auth/admins/login`. 가입·비밀번호 변경 없음. 로컬 관리자 1명(`admin@tickting.local`)은 **`db/seed/V103`의 시드**로 넣고, 저장소에는 BCrypt 해시만 있고 비밀번호는 팀에서 따로 전달한다. 시드는 로컬에서만 적용하고 운영 관리자 계정은 배포 때 따로 만든다. (확정)
- **권한은 두 단계** (2026-11-12): ① 계정 종류·역할은 시큐리티가 토큰으로 검사(`SecurityConfig` 경로 규칙: 공개 조회 GET, 예매자 전용, `/seller/**`, `/admin/**`, 대표 전용은 `@PreAuthorize("hasRole('SELLER_OWNER')")`), ② "내 것인가"는 서비스가 토큰의 번호로 조회하고 남의 것은 404. 판매자 대표 전용으로 확정된 기능은 담당자 초대·비활성화(확장)뿐이고, 공연·회차 취소와 취소 규정 설정을 대표 전용으로 할지는 미정. (확정)

### 공연장·좌석 (2부)
- 구조: **공연장 → 구역 → 좌석** 3단계. 공연장별 테이블 분리 없음(데이터만 다름).
- 열·좌석 번호는 **문자열** + `sort_order`. 스탠딩도 구역 + 번호로 동일 처리. 좌표 컬럼 없음.
- 한 구역은 한 등급. 색이 갈리는 구역은 나눔.
- **프론트가 좌석도를 그림**: 백엔드는 좌석 명단만 제공. `venue.layout_key`가 도면을 고르고, 비어 있으면 기본 격자.
- 좌석 조회는 2단계 (구역 요약 → 구역 상세). DB 먼저, 부하 테스트로 측정한 뒤 Redis 캐시.
- 공연장은 관리자가 **JSON → 생성 스크립트**로 만듦 (앱 시작 시 시드, `POST /admin/venues`). 한 트랜잭션.
- 공연이 잡힌 공연장의 좌석 행은 수정·삭제 금지.
- 공연장 삭제는 `status`(사용 중지). `venue_request`는 **테이블만** 두고 소통은 사이트 밖(메일·전화).
- **추상화 범위**: 인터페이스·전략 패턴은 **락 방식과 외부 연동 경계(인증, 결제)**에만. 좌석 배치와 좌석 배정에는 쓰지 않음.

### 공연·판매 좌석 (3부)
- **판매 상태는 회차**(`ON_SALE/PAUSED/POSTPONED/CANCELED`). 공연은 `DRAFT/PUBLISHED/CANCELED`. 예정·종료·매진은 계산.
- 판매 오픈·종료·1인 최대 매수는 공연 단위. 예매 수수료는 **공연마다 판매자가 설정**, 대기열·캡챠는 **서비스 고정**(테이블·컬럼 없음).
- 가격은 **등급마다 1개**(가격 종류 없음). 구역에 등급을 지정(`zone_grade`), 지정 안 한 구역은 판매 제외.
- 회차는 먼저 만들고, 판매 오픈 **24시간 전**(오픈 당일 아님) 스케줄러가 공연장 좌석을 **복사해 `schedule_seat` 생성**(가격도 복사, `zone_id` 포함). 회차 1개 = 트랜잭션 1개. 이미 오픈 24시간 안이면 회차 추가 즉시 생성. (2026-11-10 변경)
- 좌석 상태 5가지: `AVAILABLE / HELD(임시 점유) / SOLD / BLOCKED(판매 제외) / RESERVED(판매자 보류)`.
- 좌석을 만든 뒤에는 등급·가격 수정 불가, 예매가 생기면 회차 일시 수정 불가(연기로 처리). 같은 공연장에서 시간이 겹치는 회차 등록 불가.
- 매진은 신경 쓰지 않음. (목록의 "매진" 계산을 최적화하지 않는다. 경험상 매진이 없는 공연이 대부분)
- 수령 방법: 현장 / 배송 / 둘 다(예매자 선택). 장르: 콘서트·뮤지컬·연극·클래식·기타.
- 연기: "새 일정 미정" 허용. 무료 취소 기간은 판매자 입력(기본 14일). 연기 처리 시 바뀌는 곳은 회차 1행 + 연기 이력 1행 + 감사 로그 1행.
- 기본 취소 규정: 7일 전까지 0%, 6~3일 10%, 2~1일 20%, 당일 취소 불가. 판매자는 복사해서 수정.
- **끝난 회차의 `schedule_seat`는 일정 기간(예: 30일) 뒤 삭제**. (예매에 스냅샷이 있다는 전제)
- 공연 상세 화면에는 판매자 정보(회사명, 대표자, 사업자번호, 문의 연락처)를 보여줌.

### 예매·결제 (4부)
- 구성: `booking` + `booking_seat` + `payment` + `refund`. `booking : payment = 1 : N`.
- 좌석 점유 후 **7분** 안에 결제. 1인 최대 매수는 **공연 전체 누적** 기준.
- **부분 취소 지원** (좌석 단위). 예매 상태: `PENDING/PAID/PARTIAL_CANCELED/CANCELED/EXPIRED`. 환불 상태는 `refund`가 가짐.
- `booking_seat`는 구역·열·번호·등급·가격을 **스냅샷**으로 저장하고, `schedule_seat_id`는 NULL 허용.
- 취소 규정은 예매에 **jsonb 스냅샷**으로 복사.
- 배송은 `booking` 컬럼(받는 사람, 주소, 택배사, 송장번호). 배송 테이블 없음. 조회는 택배사 링크로 연결.
- 중복 판매 방지는 3중: `SELECT ... FOR UPDATE`(기본) → `version`(낙관적 락 비교 실험용) → `booking_seat`의 부분 UNIQUE 인덱스 `WHERE active`.
- 금액은 서버가 계산하고 토스 승인 때 비교. 결제 수단은 토스 결제창.
- 환불: 자동 3회 재시도 후 관리자 수동 처리. 환불 사유에 `SYSTEM`(자동 처리) 포함.
- 예매 수수료는 취소 시 **환불**(임시 결정, 정책에 따라 변경 가능).
- **좌석 점유와 PENDING 예매 생성은 한 트랜잭션**. `booking.performance_id` 추가. (2026-11-10)
- **1인 최대 매수**: `booking_seat` 활성 좌석을 세서 검사하고, 사용자·공연 단위 잠금(advisory lock)으로 동시 요청을 막음. 취소·만료 좌석은 한도에서 제외, 한도 수정은 예매가 생긴 뒤 늘리기만 가능 (모두 임시). 같은 사용자 동시 요청 테스트를 만든다.
- **환불 중복 방지**: `refund.idempotency_key`(토스 멱등 헤더) + 상태 `PROCESSING`. 요청 도중 서버가 죽어도 이중 환불이 안 되게.
- 연기 무료 취소 판단: 최신 연기 이력의 `free_cancel_until`이 안 지났고 + 예매가 그 연기 이력보다 먼저 생긴 경우만. 판단은 한 클래스에서만.

### 운영 (5부)
- `audit_log`: 판매자·관리자·시스템의 **변경 행동만**, 전·후 값은 `jsonb`, **추가만 하고 수정·삭제 없음**, FK 없음. 판매자는 자기 사업체 로그만 조회.
- 로그 보관 기간 제한 없음. 많아지면 오래된 것을 파일(JSON Lines 등)로 S3 같은 곳에 옮김(확장).
- 스케줄러: 만료 점유 정리(1분), 결제 불일치 보정(5분, 토스 조회), 환불 재시도·일괄 환불, 끝난 회차 좌석 정리(하루 1회), 판매 좌석 생성(1시간, 오픈 24시간 전부터).
- 환불 실패 알림은 관리자 화면 목록으로 표시 (이메일·슬랙은 확장).

### 인프라·배포 (2026-11-12)
- **로컬/운영 구분**: 로컬은 Docker Compose + Nginx + 앱 여러 개 + PostgreSQL·Redis 컨테이너, 운영은 AWS ALB + Auto Scaling Group. 앱 코드는 로드밸런서 종류와 무관하게 같다. (확정)
- **로컬 검증 범위**: 정합성(좌석 중복 판매, 1인 최대 매수, 스케줄러 중복, 서버 간 상태 공유)은 로컬에서 검증. 자동 증설은 운영에서만 검증. (확정)
- **성능 측정**: 로컬은 Docker CPU·메모리를 운영 사양에 맞춰 제한하고 같은 k6 시나리오로 개선 전후를 상대 비교, 운영(EC2)에서 같은 시나리오로 재측정. (확정)
- **배포 순서**: 1주차 EC2 한 대 + Docker(공개 URL) → 3주차 RDS·Redis·ALB + 앱 서버 수동 2대 → 여유 있으면 Auto Scaling Group(예약 증설 + 부하 기준 증설). (임시)
- **로드밸런서**: Nginx는 로컬에서만 쓰고 운영은 ALB. 서버를 자동으로 늘리고 줄이려면 ALB와 Auto Scaling Group이 짝이기 때문. (임시)
- **요청 빈도 제한**: Nginx가 아니라 앱 + Redis로 구현. 실제 사용자 IP는 `X-Forwarded-For`로 읽는다. (임시)
- **Redis 운영 위치**: 서버 안이 아니라 밖에 둔다(서버가 수시로 생기고 사라지므로). AWS ElastiCache(클러스터 모드 끔)와 EC2 컨테이너 중 선택. (미정)
- **이미지 저장소**: AWS ECR. EC2에 부여한 IAM 역할로 받아서 서버에 로그인 토큰을 두지 않는다. Docker Hub로 바꿔도 구조는 같다. (임시)
- **증설 지표**: CloudWatch(EC2 CPU, ALB 요청 수)를 Auto Scaling Group이 읽는다. 앱 내부 지표(TPS, 응답 시간, 커넥션 풀)는 Prometheus + Grafana. (임시)
- **운영 조건**: 지급 크레딧 약 7만 원, 서버는 09~18시에만 가동. 상시는 EC2 한 대(앱, PostgreSQL, Redis 컨테이너)로 두고, ALB·다중 서버·RDS·ElastiCache는 부하 테스트와 시연 기간에만 만들고 삭제. 운영 compose에는 DB 볼륨과 재시작 정책을 지정. (확정, 세부 조건은 확인 필요)
