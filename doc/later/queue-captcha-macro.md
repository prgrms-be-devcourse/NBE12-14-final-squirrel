## 이미 정해진 것

| 항목 | 내용 | 출처 |

| 대기열·캡챠는 **서비스 고정 정책** | 판매자가 선택하지 않음. 테이블·컬럼 없음. 설정 파일 값으로 처리 | 3부 |
| 구현 수단 | 테이블 없이 **Redis와 코드**로 처리 | 부록 A |

| 1인 최대 매수 | 공연 전체 누적, 사용자·공연 단위 잠금으로 동시 요청 방어 | 4부 4-7 |
| 좌석 점유 시간 | 7분 | 4부 |

## 정해야 할 것

| 주제 | 질문 | 메모 |
|---|---|---|
| 대기열 방식 | 어떤 자료구조로, 누구를 몇 명씩 들여보낼까? | Redis `ZSET`(대기 순번) + 입장 토큰(짧은 만료)이 일반적. 동시 입장 인원 수를 설정으로 |
| 대기열 적용 범위 | 공연 전체? 회차별? 오픈 직후 몇 분만? | 판매 오픈 시각 이후 일정 시간만 켜는 방식도 가능 |
| 입장 토큰 검증 | 좌석 점유 API가 토큰을 어떻게 확인할까? | JWT와 별도로 Redis 키 확인, 점유 요청마다 검증 |
| 캡챠 위치 | 대기열 입장 전? 좌석 선택 전? 결제 전? | 매크로는 보통 입장과 좌석 선택에서 많이 쓰임 |
| 캡챠 종류 | 직접 만들까, 외부 서비스(reCAPTCHA 등)를 쓸까? | 포트폴리오에서는 흐름과 검증 서버 구조가 핵심 |
| 요청 빈도 제한 | 사용자·IP·계정 종류별로 초당 몇 번? | Redis 카운터(슬라이딩 윈도우 등). Spring Security 필터 위치 결정 |
| 다중 세션 | 같은 계정으로 동시에 여러 대기열/점유를 허용할까? | 1인 최대 매수 잠금과 함께 설계 |
| 판매 중지·재개와의 관계 | 중지 때 대기열 인원은 유지? 재개 때 재구성? | 유스케이스 UC-S17의 미결 사항 |
| 핑거프린트 | 도입할까? | 보류 항목. 개인정보·동의 범위 확인 필요 |

## 설계할 때 참고할 연결점

- 좌석 점유 트랜잭션(4부 4-6, 4-7)의 **앞단**에 대기열 토큰 검증과 빈도 제한을 둔다. 뒤쪽 DB 방어(락, 부분 UNIQUE)는 그대로 유지한다.
- Redis 키에는 항상 **계정 종류를 붙인다** (`USER:5`). (`operations-and-performance-review.md` A-8)
- 대기열이 있으면 구역 요약 조회와 좌석 점유 부하가 줄어든다. 그래도 **부하 테스트로 대기열 없는 상태와 있는 상태를 비교**하면 포트폴리오에서 설명하기 좋다.
- 지금은 Redis 설정이 없다. 대기열 설계 시점에 같이 만든다. (`README.md` 보류 항목)
