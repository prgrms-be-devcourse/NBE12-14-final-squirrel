## 정해 둔 것

- **판매자 이메일은 전역 유일 그대로.** 한 이메일 = 한 사업체. 한 사람이 여러 회사 담당자가 되는 경우는 고려하지 않는다.

## A. 구현할 때 조심할 것 (설계는 그대로)

좌석 점유·결제를 구현할 때 이 목록을 다시 보세요.

| # | 주의할 것 | 이유와 방법 |
|---|---|---|
| 1 | **토스 호출을 DB 트랜잭션 안에 넣지 않는다** | 결제 승인은 `검증 (트랜잭션 1) → 토스 호출 (트랜잭션 없음) → 결과 반영 (트랜잭션 2)`로 나눈다. 호출 중에 DB 연결과 좌석 락을 잡고 있으면 토스가 느려질 때 커넥션 풀(기본 10개)이 바로 바닥난다. 호출과 반영 사이가 끊기는 구간이 5부 "결제 불일치 보정"이 필요한 이유다. |
| 2 | **좌석 점유는 조건부 UPDATE 한 문장이 유리하다** | `UPDATE schedule_seat SET status='HELD', ... WHERE id = ANY(:ids) AND status='AVAILABLE'`를 쓰고 영향 행 수가 요청 수와 다르면 롤백한다. `SELECT FOR UPDATE` 뒤 `UPDATE`보다 락을 잡는 시간이 짧고 왕복이 줄어든다. 락 대기가 길어지지 않게 `lock_timeout`이나 `NOWAIT`으로 "이미 선택된 좌석"을 빨리 응답한다. 락 방식은 전략 패턴으로 바꿔 끼울 수 있게 둔 부분이라 비교 실험도 가능하다. |
| 3 | **스탠딩은 좌석 선택이 아니라 자동 배정** | 500석 중 N장을 `FOR UPDATE SKIP LOCKED LIMIT N`으로 집는다. 여러 사람이 같은 구역에 몰려도 서로 기다리지 않는다. |
| 4 | **만료 점유 사이의 틈** | 스케줄러는 1분마다 돌지만 `held_until`은 이미 지났는데 정리가 안 된 구간이 최대 1분 있다. 점유 조건에 "만료된 `HELD`는 점유 가능으로 본다"를 넣을지 정한다. 반대로 결제 승인 때는 내 점유가 아직 유효한지(`held_until`) 다시 확인한다. 안 하면 만료 뒤 다른 사람이 가져간 좌석에 결제가 성립한다. |
| 5 | **토스 결제창 시간과 7분의 관계** | 결제창을 연 뒤 승인까지 7분에 가까우면 4번에 걸린다. 점유는 8분, 화면 표시는 7분처럼 여유를 두는 방법도 있다. |
| 6 | **스케줄러 중복 실행** | 서버가 2대가 되면 결제 불일치 보정, 환불 재시도도 두 번 돈다. 만료 정리는 `SKIP LOCKED`가 있지만 나머지는 ShedLock 같은 방식이 필요하다. |
| 7 | **환불 금액 반올림** | 좌석마다 원 단위로 절사하면 합계가 "전체 금액 × 비율"과 몇 원 어긋난다. 기준을 정하고, 부분 취소를 여러 번 한 뒤 환불 합계가 결제 금액을 넘지 않는지 테스트한다. |
| 8 | **세 계정 테이블의 `id` 충돌** | 사용자 5번과 판매자 5번이 공존한다. Redis 블랙리스트 키, 로그 키, 캐시 키에 항상 계정 종류를 붙인다 (`USER:5`). |
| 9 | **`deleted_at IS NULL` 조건 누락** | `@SQLRestriction`을 전역으로 쓰지 않으므로 빼먹기 쉽다. 회원 조회 메서드를 몇 개로 한정한다. |

| # | 문제 | 설명 | 대응 |
|---|---|---|---|
| 1 | 구역 요약 조회 | 오픈 순간 모든 사용자가 `group by zone, count(AVAILABLE)`를 반복한다. 쓰기와 섞여서 index-only 스캔도 잘 안 된다. | 부하 테스트에서 측정한 뒤 Redis로 간다. 1~2초 정도의 짧은 캐시도 충분하다. |
| 2 | 끝난 회차 좌석 삭제 후 판매자 통계 공백 | 30일 뒤 `schedule_seat`를 지우면 "총 좌석, 잔여 좌석"을 보여 주는 현황 조회(UC-S09)가 끝난 회차에는 불가능해진다. | 삭제 전에 회차별 요약(총 좌석, 판매 수, 매출)을 남기거나, 통계를 `booking_seat`만으로 계산하게 한다. 삭제는 회차 단위로 쪼개서 지운다. |
| 3 | `audit_log`, `refund` 무한 증가 | 로그는 추가만 하고 시스템 자동 보정도 기록한다. | 월 단위 파티션을 고려한다. 인덱스는 `(business_id, created_at DESC)`면 충분하다. |
| 4 | 일괄 환불 처리 시간과 토스 호출 한도 | 취소 건이 수천 건이고 호출당 0.3~0.5초면 직렬 처리에 수십 분이 걸린다. 토스 요청 한도도 있다. | `REQUESTED` 큐에 쌓아 차례로 처리하되 한 번에 처리하는 개수와 속도를 설정으로 조절한다. |
| 5 | `READY` 결제 행이 쌓임 | 예매 시도마다 `payment(READY)`가 생긴다. 만료된 예매의 `payment` 상태가 "FAILED 또는 그대로"라 모호하고, 보정 스케줄러가 이 행들을 계속 훑는다. | `payment (status, created_at)` 인덱스를 두고, 만료 처리 뒤에는 `EXPIRED`처럼 더 안 훑는 상태로 확정한다. 단 만료 직전에 결제했을 수 있어서 토스에 한 번 조회한 뒤에 확정한다. |
