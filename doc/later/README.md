## 보류한 기능

| 기능 | 왜 보류했나 | 할 때의 방향 | 언제 |
|---|---|---|---|
| 취소 규정 삭제 → **보관(소프트 삭제)** | 실제 삭제는 막는다. 공연(공개·작성 중·취소 모두)이 `cancel_policy_id`로 규정을 가리키고 논리 FK라, 지우면 공연 상세의 취소·환불 안내가 사라지고 깨진 참조가 남는다. 삭제가 없으면 규정이 쌓인다(개수 상한 없음, 공개 공연이 쓰는 규정은 고칠 수 없어 새로 만듦) | 행을 지우지 않고 `deleted_at`만 채운다(`SoftDeletableEntity`, `findBy…DeletedAtIsNull`). 보관한 규정은 목록·공연 등록 선택에서 빠지고, 이미 쓰는 공연에는 그대로 보인다. 그래서 "쓰는 공연이 있는가" 검사가 필요 없다. 기본 규정은 보관할 수 없다. 컬럼 추가(마이그레이션)와 명세(SLR-19~22)가 필요하다 | 판매자 화면에서 규정 목록이 불편해질 때 |
| 등급 삭제 API (`DELETE /api/v1/seller/performances/{performanceId}/grades/{gradeId}`) | 팀 문서(`api-spec` SLR-09·10)에는 등급 추가와 수정만 있고 삭제가 없다. 삭제가 없으면 잘못 만들었거나 안 쓰기로 한 등급이 판매자의 등급 목록에 남는다. 예매자에게는 영향이 없다(예매자 공연 상세는 구역에 지정된 등급만 가져온다). 남은 등급은 SLR-10으로 이름·가격을 고쳐 다른 등급으로 쓸 수 있다 | `api-spec`에 먼저 넣고 팀과 맞춘 뒤 만든다. 삭제 조건 후보: 공연이 취소되지 않았고, 좌석을 만들기 전(`locked`가 false)이고, 어느 구역도 그 등급을 지정하지 않았을 때만. 새 에러 코드가 필요하다(예: 구역이 쓰는 등급이면 409). **확인할 것**: 취소된 회차의 좌석(`schedule_seat`)은 만들 때 복사한 등급 번호를 계속 가지므로(취소 이력), `locked`가 false여도 그런 좌석이 가리키는 등급을 지우면 깨진 참조가 남는다. 이 경우를 막거나 취소 규정처럼 보관(소프트 삭제)으로 하는 방법을 정해야 한다 | 판매자가 등급을 지우고 싶다는 요구가 생기거나 등급 관리 화면을 설계할 때 |
| 공연장 수정(좌석·구역 추가·삭제) | 팀 문서에 공연장 수정 API가 없다. 공연장과 좌석은 시드로만 만든다 | 좌석·구역을 바꾸면 ① `venue.total_seats`도 같은 트랜잭션에서 다시 센다(판매 현황 SLR-17·구역 요약이 총 좌석으로 이 값을 쓰고, 판매 좌석은 공연장 좌석을 복사해 같은 값이라는 전제) ② 그 공연장을 쓰는 작성 중 공연의 구역 설정(`zone_grade`)에 새 구역은 `UNSET` 행을 만들고 지운 구역 행은 정리한다(공개 조건이 `UNSET` 0개만 봄) ③ 이미 판매 좌석이 생성된 회차는 복사본이라 그대로 두거나 막을지 정한다 | 공연장 관리 기능을 만들 때 |
| 판매자 예매 목록(SLR-18)의 개인정보 노출 다시 보기 | 알림 기능과 발송 처리 기능이 없어서, 판매자(대표·담당자 모두)에게 주문자 이름·전화번호와 배송 예매의 받는 사람 이름·연락처·주소를 그대로 준다(2026-11-19) | 알림(변경·취소 안내)이 생기면 주문자 전화번호를 가릴지, 발송 처리가 생기면 발송이 끝난 예매의 주소를 가릴지, 담당자에게 보이는 범위를 줄일지 다시 정한다 | 알림·발송 처리 기능을 만들 때 |
| 발송 처리(송장 입력)와 배송 상태 | 3부·4부는 "판매자가 발송할 때 택배사·송장번호를 입력"한다고 하지만 그 API가 없다. 지금은 판매자 예매 목록(SLR-18)에서 배송지만 볼 수 있다 | 판매자가 예매별로 택배사·송장번호를 입력하는 API, 배송 대상만 모아 보기·내려받기, 예매자 화면의 배송 조회 연결(택배사 조회 주소는 설정) | 배송 기능을 만들 때 |
| 정산(판매자가 실제로 받을 돈) | 판매자 예매 목록(SLR-18)은 수수료 없이 남은 표값만 보여 준다. 취소 수수료로 판매자에게 남는 돈, 예매 수수료, 환불액은 반영하지 않는다(예매 수수료는 취소한 좌석 몫만 환불하는 임시 정책, 2026-11-24) | 회차·공연 단위로 판매 표값, 취소 수수료 수입, 환불액, 예매 수수료를 모아 보여 주는 정산 조회. 환불(`refund`) 완료 건 기준 | 정산이 필요해질 때 |
| 공연장 수정 시 이미 등록된 공연의 구역 설정 맞추기 | 공연장 수정 기능이 없어서(시드로만 만듦) 지금은 구역 설정 행이 모든 구역에 있다고 믿는다. 판매 좌석 생성(SLR-14)은 구역 설정을 따로 검증하지 않고 복사 결과가 0행일 때만 거절한다(`PERFORMANCE503`) | 공연장에 구역·좌석을 추가·삭제할 때 이미 등록된 공연의 `zone_grade`도 함께 만들거나 지운다. 좌석 생성 전에 구역 설정 행이 모두 있는지 확인하는 검사도 그때 넣는다 | 공연장 수정 기능을 만들 때 |
| 공개할 때 오픈 24시간 안인 회차의 좌석 즉시 생성 | 지금은 공개 3시간 규칙(`PERFORMANCE406`)으로 틈을 막고, 공개 때 즉시 생성은 안 한다(2026-11-24). 좌석은 판매자 버튼이나 스케줄러가 만든다 | 공개 직후 오픈 24시간 안의 회차는 공개와 함께 만든다. 그러면 3시간 제한을 없앨 수 있다. 생성 실패 때 공개를 실패시킬지 정해야 한다 | 공개 제한을 풀고 싶을 때 |
| 판매 구역 0개 방지를 구역 설정(SLR-11)에서도 할지 | 판매 좌석 생성(SLR-14)만 판매 구역이 0개면 막는다. SLR-11은 `ASSIGNED` 최소 개수를 검사하지 않아 공개 뒤에도 모두 판매 제외로 돌릴 수 있다(정책 17⑦) | 공개된 공연의 구역 설정에서 마지막 판매 구역을 빼는 것을 막는다. 작성 중에는 구역을 하나씩 채우는 중간 상태가 필요해 조건이 갈린다 | 공개 뒤 모두 미판매로 돌리는 일이 실제로 문제가 될 때 |
| 공연장 사용 중지 기능을 만들 때 정할 것 | 공연장 상태를 바꾸는 기능이 아직 없다(DB를 직접 바꿔야 생긴다). 회차 추가(SLR-12)는 사용 중지된 공연장이면 거절하지만(`VENUE001`), 이미 있는 회차의 예매·결제·좌석 생성, 작성 중 공연의 공개, 공연장을 바꾸지 않는 공연 수정은 막지 않는다 | 기존 회차를 그대로 둘지·일시 중지·전부 취소와 환불할지, 작성 중 공연의 공개와 좌석 생성·기존 회차 예매를 막을지, 중지 사유·기간·판매자 알림을 정한다. 회차 추가의 `VENUE001` 검사를 유지할지도 같이 본다 | 공연장 관리 기능을 만들 때 |
