# 대기열 설계

> 좌석 선택 화면에 사용자가 한꺼번에 몰려도 서버와 DB가 버티도록, 정원만큼만 들여보내는 장치다.
> 부하 테스트에서 "대기열 없는 상태와 있는 상태"를 같은 조건으로 비교하려고 만들었다. 매크로 방어는 이 문서의 범위가 아니다. (캡챠와 좌석 점유 요청 횟수 제한은 `doc/api-spec.md`에 있다)

## 1. 어디서 대기열이 걸리나

회차를 고르고 **"예매하기"를 누를 때** 대기열에 들어간다. 입장한 사람만 구역 요약을 볼 수 있고, 구역을 눌러 구역 좌석을 보고 좌석을 점유한다.

| 단계 | API | 대기열 |
|---|---|---|
| 공연 목록·상세 (회차 선택) | `GET /performances`, `/performances/{id}` | 없음. 누구나 본다 |
| **예매하기 클릭** | `POST /schedules/{scheduleId}/queue` | **여기서 줄을 선다.** |
| 구역 요약 | `GET /schedules/{scheduleId}/zones` | 입장한 예매자만 |
| 구역 좌석 조회 | `GET /schedules/{scheduleId}/zones/{zoneId}/seats` | 입장한 예매자만 |
| 좌석 점유 | `POST /schedules/{scheduleId}/bookings` | 입장한 예매자만 |
| 결제 준비·승인, 내 예매 | `/bookings/**`, `/payments/**` | 없음. 점유를 끝낸 사람이라 막지 않는다 |

- 대기열은 **회차 단위**다. 좌석 경합과 부하가 회차의 좌석 화면에서 생기기 때문이다. 한 회차에 입장해도 다른 회차는 따로 줄을 서야 한다.
- 한 번 입장하면 입장 유효 시간(`entry-ttl`) 안에서는 구역 요약과 구역 좌석 사이를 오가도 다시 줄을 서지 않는다.
- 입장한 뒤에는 입장 자리가 계속 한 칸을 차지한다. 자리를 비우는 때는 아래 "자리 반납"에 있다.

### 자리 반납 (2026-11-26)

| 때 | 처리 | 이유 |
|---|---|---|
| 입장 유효 시간(`entry-ttl`)이 지남 | 비운다 | |
| 스스로 나감 (`DELETE`) | 바로 비운다 | |
| **1인 최대 매수를 결제로 채움** | 결제 승인(BKG-03) 뒤 서버가 바로 비운다 | 더 살 수 없어서 남겨 둘 이유가 없다 |
| **좌석 화면을 떠남** (뒤로 가기, 다른 화면 이동, 창 닫기, 새로고침) | 화면이 `DELETE ?delayed=true`를 보내고, 서버는 `leave-grace`(30초) 뒤에 비운다. 그 전에 돌아오면 원래 입장 만료 시각이 되살아난다 | 구경만 하고 나간 사람의 자리가 10분 남지 않게 한다 |
| 좌석 점유 성공 | **비우지 않는다.** 화면도 결제 화면으로 갈 때는 알리지 않는다 | 한도 안에서 더 점유하려면 입장이 필요하다 |
| 결제했지만 더 살 수 있음, 결제 대기 좌석으로만 한도를 채움 | 비우지 않는다 | 반납하면 더 사려고(또는 대기 좌석이 만료된 뒤 다시 잡으려고) 줄을 처음부터 다시 선다 |

- **바로 비우지 않고 유예를 두는 이유:** 화면은 새로고침·창 닫기·뒤로 가기를 믿을 만하게 구분할 수 없다. 바로 비우면 새로고침만 해도 줄 맨 뒤로 간다.
- 되살리는 요청은 줄 서기·상태 확인(`queue-poll.lua`)과 좌석 조회·점유의 입장 확인(`queue-check.lua`)이다. 여러 번 알려 와도 원래 만료 시각을 덮어쓰지 않고 유예가 늘어나지 않는다. (`queue-leave-soon.lua`)
- 대기 중인 사람에게 `delayed`는 아무 일도 하지 않는다. 대기자의 이탈은 지금처럼 화면의 즉시 `DELETE`와 `waiting-timeout`이 처리한다.
- 결제 뒤 반납이 실패해도 결제는 성공이고, 자리는 유효 시간이 지나면 비워진다. 결제 보정 작업이 확정한 예매는 따로 반납하지 않는다. (승인 5분 뒤에 도는 작업이라 입장 시간이 대부분 지났다)
- 같은 회차를 탭 두 개로 연 사람이 하나를 닫으면 30초 유예가 걸린다. 남은 탭에서 그 안에 좌석을 보거나 점유하면 유지되고, 아무것도 하지 않으면 다음 요청에서 `QUEUE000`이 나와 다시 줄을 선다.

## 2. API (예매자 전용)

공통 응답 `ApiResponse<T>`. `data`는 아래와 같다.

```json
{ "status": "WAITING", "position": 3, "waitingCount": 120, "expiresAt": null }
{ "status": "ADMITTED", "position": null, "waitingCount": null, "expiresAt": "2026-11-19T10:30:00" }
{ "status": "NONE", "position": null, "waitingCount": null, "expiresAt": null }
```

| 메서드·경로 | 설명 |
|---|---|
| `POST /api/v1/schedules/{scheduleId}/queue` | 줄을 선다. 자리가 있으면 바로 `ADMITTED`. 이미 줄에 있거나 입장해 있으면 순번·입장 상태를 바꾸지 않고 현재 상태를 준다. 지금 예매할 수 없는 회차는 `BOOKING002`(400), 없는 회차는 `BOOKING004`(404) |
| `GET /api/v1/schedules/{scheduleId}/queue` | 내 상태. 대기 중이면 2~3초마다 부른다. 부르는 것이 "아직 기다린다"는 표시다 |
| `DELETE /api/v1/schedules/{scheduleId}/queue` | 줄에서 나가거나 입장 자리를 반납한다. 줄에 없어도 성공. `?delayed=true`면 입장 자리를 `leave-grace` 뒤에 비운다(위 "자리 반납") |

- 입장하지 않은 사람이 구역 요약·구역 좌석 조회·좌석 점유를 부르면 **403 `QUEUE000`**이다. 구역 요약·좌석 조회는 로그인하지 않으면 401, 예매자가 아니면 403(`AUTH100`)이다.
- `status`가 `NONE`이면 줄에도 입장 목록에도 없다. 입장 시간이 지났거나, 나갔거나, 오래 확인하지 않아 밀려났다. 다시 입장한다.
- 프론트 흐름: 예매하기 → `POST` → `ADMITTED`면 구역 요약 화면, `WAITING`이면 대기 화면에서 `GET`을 반복 → `ADMITTED`가 되면 구역 요약 화면으로.

## 3. 동작 (Redis)

상태는 모두 Redis에 있다. 앱은 상태가 없어서 서버가 여러 대여도 어느 서버로 가든 같은 결과가 나온다. DB는 쓰지 않는다.

| 키 (`tickting:queue:{회차}:…`) | 종류 | 내용 |
|---|---|---|
| `wait` | ZSET | 대기자. 멤버 `USER:번호`, 점수 도착 순번(카운터) |
| `active` | ZSET | 입장자. 멤버 `USER:번호`, 점수 만료 시각(ms) |
| `seq` | 문자열 | 도착 순번 카운터 |
| `seen:USER:번호` | 문자열 | 대기자의 마지막 상태 확인 표시(30초 만료) |
| `open` | 문자열 | 이 회차가 입장을 받을 수 있다고 DB로 확인한 표시(10초 만료) |
| `keep:USER:번호` | 문자열 | 좌석 화면을 떠난 입장자의 원래 만료 시각(유예 동안만) |

- 키에는 계정 종류(`USER`)를 붙인다. 예매자·판매자·관리자는 번호가 겹칠 수 있다. 회차 번호는 중괄호로 묶어 같은 회차의 키가 같은 슬롯에 놓이게 했다. (클러스터로 옮겨도 스크립트가 돈다)
- **입장 처리는 Lua 스크립트(`redis/queue-poll.lua`) 하나로 원자적으로 한다.** 만료된 입장자 정리 → (필요하면) 줄 서기 → 빈 자리만큼 앞에서부터 입장 → 내 상태 계산. Redis가 스크립트를 한 번에 하나씩 실행하므로 서버가 여러 대여도 정원이 넘지 않고 순서가 섞이지 않는다.
- **별도 스케줄러가 없다.** 입장 처리는 줄 선 사람이 상태를 확인(폴링)할 때 같이 한다. 대기자는 어차피 몇 초마다 확인하고, 그 순간 빈 자리만큼 앞사람부터 입장시키기 때문이다. 스케줄러를 두면 서버마다 돌려서 중복 실행을 막는 장치가 따로 필요하다.
- 시각은 서버 시계가 아니라 Redis `TIME`을 쓴다. 서버마다 시계가 달라도 만료가 어긋나지 않는다.
- **유령 대기자**: 화면을 닫고 떠난 사람은 `seen` 표시가 사라진다. 앞사람이 되어도 자리를 주지 않고 건너뛴다. (순번 숫자에는 줄 앞에 닿기 전까지 포함되어 실제보다 크게 보일 수 있다)
- 줄 서기 전에 "지금 예매할 수 있는 회차인지"를 `ScheduleService.getBookable`로 확인한다. 없는 번호나 판매 중이 아닌 회차로 Redis 키가 쌓이지 않게 하려는 것이다. 확인 결과는 10초 기억해서 오픈 순간에도 요청마다 DB를 읽지 않는다. (`QueueFacade`)

### 이메일 인증은 여기서 확인하지 않는다

이메일 인증은 **가입 전에** 마친다(`doc/api-spec.md` "가입 전 이메일 인증 (AUTH-17·18)"). 가입한 회원은 모두 인증을 마친 상태라 대기열 입장(`POST`)에서 확인하지 않는다. (2026-11-24 변경. 2026-11-23에는 입장 때마다 DB에서 인증 여부를 읽어 미인증이면 403 `AUTH307`이었다)

- **왜 뺐나:** 가입이 곧 인증이라 평소에는 한 번도 걸리지 않는 검사인데, 오픈 순간 입장이 몰릴 때 모든 입장에 DB 조회가 한 번씩 붙는다. 대기열이 DB로 가는 부하를 줄이려는 것인데 그 앞에서 DB를 먼저 읽는 것은 목적에 어긋난다. (실제 영향은 측정하지 않았다)
- **함께 잃은 것:** 이 검사의 쿼리는 `deleted_at IS NULL`도 봐서 **탈퇴한 회원이 토큰·세션이 남은 동안 입장하지 못하게** 하는 효과를 겸했다. 탈퇴한 기기의 세션만 지워지고 다른 기기 세션·v1 액세스 토큰은 남아서(`api-spec.md` AUTH-08) 탈퇴 직후 최대 15~30분 동안 입장해 줄에 설 수 있다. 입장 차례가 되어도 좌석 점유 앞의 회원 조회(`BookingFacade`, 404 `USER002`)에서 막혀 예매는 못 한다. 줄에서 자리 하나를 차지하는 정도이고, 세션을 회원 번호로 찾아 지우는 변경(별도 PR)과 v1 삭제가 끝나면 사라진다.

## 4. 입장 확인 (인터셉터)

`QueueAdmissionInterceptor`가 구역 요약, 구역 좌석 조회, 좌석 점유 요청 앞에서 "로그인한 예매자가 이 회차에 입장해 있는가"를 확인한다. 대상 경로는 `WebMvcConfig`에서 정한다.

- 공연·예매 도메인의 컨트롤러·서비스는 대기열을 모른다. 그 코드는 바꾸지 않았다.
- 구역 요약·좌석 조회는 `SecurityConfig`의 `PUBLIC_READ_PATHS`에 그대로 있다. 로그인·예매자 확인은 인터셉터가 한다. (대기열을 끄면 `enabled=false`로 이 확인도 함께 사라져 지금처럼 공개 조회로 돌아간다)
- 확인은 Redis 한 번이다. (`redis/queue-check.lua`) 유예 중인 사람이면 같은 스크립트가 원래 만료 시각을 되살린다.
- 입장 확인은 입장 목록(`active`)에서 만료 전인지만 본다. 한 번 입장한 사람은 그 시간 안에는 요청마다 줄을 거치지 않는다.

## 5. 설정 (`application.yaml`의 `app.queue`)

| 키 | 값 | 설명 |
|---|---|---|
| `enabled` | `true` | 끄면 누구나 바로 입장한 것으로 본다. 테스트·로컬 확인용 |
| `max-active` | `1000` (임시) | 회차마다 동시에 입장해 있을 수 있는 인원. 부하 테스트로 정한다 |
| `entry-ttl` | `10m` (임시) | 입장 유효 시간 |
| `waiting-timeout` | `30s` | 이 시간 동안 상태 확인이 없으면 떠난 것으로 본다. 화면 확인 주기(2~3초)보다 충분히 길게 둔다 |
| `leave-grace` | `30s` (임시) | 좌석 화면을 떠난다고 알려 온 뒤 자리를 비우기까지의 시간 |

`max-active`는 앱 서버가 버티는 요청 수에 맞춘다. 부하 테스트에서 앱 2 CPU의 읽기 한계가 초당 약 1,000건이었고, 입장한 사람 한 명은 요청을 한꺼번에 보내지 않으므로 그 한계보다 여유 있게 잡는다. 대기열 없이 잰 결과(`doc/load-test-plan.md` 14장)와 같은 조건으로 다시 재서 값을 정한다.

## 6. 일부러 하지 않은 것 (나중에)

- **매크로 방어**: 대기열은 서버가 터지지 않게 하는 장치지 매크로를 막지 못한다. 캡챠(입장)와 좌석 점유 요청 횟수 제한은 대기열 밖에서 건다. 남은 방어는 `doc/later/queue-captcha-macro.md`.
- 판매 중지·재개와 대기 인원의 관계. 지금은 판매 중이 아닌 회차가 되면 새로 줄을 설 수 없고, 이미 입장한 사람은 점유 단계에서 판매 조건 검사에 걸린다.
- 예상 대기 시간. 순번과 전체 대기 인원만 준다.
- 입장 후 점유에 성공하면 자리를 반납하는 정책. 필요하면 나중에 바꾼다. (반납하는 때는 1장 "자리 반납")
- 대기열 상태를 푸시로 알리기(SSE·웹소켓). 지금은 폴링이다.

## 7. 테스트

`QueueApiTest`(실제 PostgreSQL·Redis): 정원 안은 바로 입장·정원 밖은 순번(재진입해도 순번 유지), 나가면 앞사람 입장, 떠난 대기자 건너뜀, **동시에 12명이 들어가도 정원만큼만 입장하고 순번이 겹치지 않음**, 입장하지 않으면 구역 조회·점유 403, 로그인하지 않으면 401·다른 회차 입장은 통하지 않음, 입장 만료, 판매 중이 아닌 회차·없는 회차 거절, 떠난다고 알린 뒤 돌아오면 원래 만료 시각 유지·돌아오지 않으면 다음 사람 입장, 최대 매수를 결제한 사람만 자리 반납, 반납이 실패해도 결제 성공. 다른 통합 테스트는 대기열을 끈 상태(`app.queue.enabled=false`)로 돈다.
