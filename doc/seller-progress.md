## 확정한 정책

1. **공개 후 공연 수정(SLR-03)은 팀 정책을 따름 (2026-11-13, 개정)**: 처음에는 공개 후 수정을 전부 막기로 했으나 팀 문서가 공연장·취소 규정만 못 바꾸게 설계해 팀 정책을 우선한다. 취소 공연은 수정 불가(409), 예매가 생긴 뒤 `maxPerPerson`은 늘리기만(임시). 폐기한 안(전체 불가)의 이유: 판매 일시·수령 방법·수수료는 돈과 연결됨. 버린 대안: 필드별 잠금(필요해지면 추가).
2. **공개(SLR-04) 조건 (2026-11-13)**: 공개 후에는 고칠 수 없고 좌석 0개 공연이 생길 수 있어 `DRAFT`(아니면 409), 판매 필드 5개, 회차 1개 이상, `UNSET` 구역 0개, `ASSIGNED` 1개 이상을 모두 만족해야 한다. 조건은 정책 18에서 늘었다.
3. **인덱스·제약·유니크 키는 TODO로만 남김 (2026-11-13)**: 마이그레이션 번호가 팀 공용이라 모아서 정한다. 감수: 그동안 서비스의 사전 확인이 유일한 방어선(동시 요청에 뚫림).
4. **공연장 목록(SLR-01) (2026-11-13)**: 문서에 검색·정렬·크기가 없었다. 사용 중 공연장만, `region` 정확 일치, `keyword`는 이름 부분 일치(주소 제외), 이름순(같으면 번호순), 기본·최대 20. 선택용 소수 데이터라 이름순이 찾기 쉽다. 버린 대안: 최신순, 지역 부분 일치, 주소 검색, 최대 50. 이름 검색은 인덱스를 못 타지만 수십 곳이라 TODO에 안 올림.
5. **내 공연 목록·상세(SLR-05·06) (2026-11-13)**: 정렬과 회차 수 범위가 없었다. 최신 등록순(같으면 번호 큰 순), 기본·최대 20, 상태를 안 주면 취소 포함. `scheduleCount`와 상세 `schedules`는 취소·연기 회차 포함(이력이 빠지면 안 되고 숫자가 맞아야 함), 회차는 공연 일시순, 이미지는 `sortOrder`순. 남의 공연·없는 공연은 같은 404 `PERFORMANCE000`. 버린 대안: 취소 회차 제외, 이름순.
6. **취소 규정 목록(SLR-19) (2026-11-15)**: 팀 공통 목록 구조대로 페이지 응답(기본·최대 20), 기본 규정을 첫 페이지 맨 앞, 내 규정은 최신순 고정. 개수 상한·삭제가 없고 잠긴 규정은 새로 만들게 되어 쌓이므로 처음부터 페이징(나중에 붙이면 화면 동작이 바뀜). 버린 대안: 페이징 없음, 최대 50, 이름순.
7. **공연 등록(SLR-02) 입력 규칙 (2026-11-15)**: 필드 범위·에러 코드가 없었다. 공연명 필수·200자·중복 허용, 연령 0~100, 러닝타임 1~1440분, 이미지 주소는 `http(s)://`·공백 없음·2048자(2026-11-16 팀 공지로 http 허용), 출연진·공지·안내는 무제한(공백뿐이면 `null`). 판매 필드는 비워도 되고 둘 다 있으면 종료 > 오픈(`PERFORMANCE001`, 과거 검사는 공개에서). `maxPerPerson` 1~5, `bookingFee` 0~10,000원, 이미지 장수 무제한은 **임시**. 없는 공연장 404 `VENUE000`, 사용 중지 400 `VENUE001`, 볼 수 없는 규정 404 `PERFORMANCE100`. 구역 없는 공연장도 등록 가능. 공연·이미지·구역 `UNSET`은 한 트랜잭션. 버린 대안: 판매 필드 필수, 등록 때 과거 검사, 길이 상한.
8. **취소 규정 상세(SLR-20) (2026-11-16)**: 기본 규정과 내 규정만, 남의·없는 규정은 같은 404 `PERFORMANCE100`. 구간은 `daysFrom` 큰 순(명세 예시와 같고, 입력 순서가 자유라 서버가 정해야 화면이 일정).
9. **`editable`은 SLR-22에서 넣음 (2026-11-16, 개정)**: 처음에는 넣지 않기로 했으나, 공개 공연이 쓰는 규정은 늘 잠겨 모르면 다 고친 뒤 409를 받고 프론트가 알 방법이 없다. 목록·상세에 넣고 잠금 검사와 같은 조회로 계산(기준 일치). 서버는 수정 때 다시 검사. 버린 대안: 넣지 않음, 상세에만.
10. **취소 규정 생성(SLR-21) (2026-11-16)**: 구간은 **양끝 날짜 포함**(`3~6`은 3~6일 전, `1~1` 허용). 명세·기본 규정 예시가 이 해석일 때만 빈틈 없이 이어진다. 구간 오류(뒤집힘, 당일부터 아님, 마지막 제한 없음 아님, 빈틈·겹침)는 400 `PERFORMANCE101`, 이름 중복(대소문자 무시)·기본 규정 이름은 409 `PERFORMANCE104`. 구간 1~10개, 일수 0~90, 수수료율 0~100, 이름 50자, 순서 자유, 대표·담당자 모두. 전 구간 취소 불가도 허용("1개 이상 가능" 조건은 `90~null 100%`로 쉽게 우회되고, 예매자 보호 바닥선은 예매처 공통 규칙의 몫). 버린 대안: 끝 날짜 제외, 취소 가능 구간 필수. 범위 밖: 정액 수수료(장당 N원)는 % 구조로 표현 못 함(컬럼·스냅샷·계산이 바뀜). 판매자는 먼 구간을 0%·10%로 비슷하게 운영.
11. **수정 잠금에 취소 공연 포함 (2026-11-16, 개정)**: 처음에는 `PUBLISHED`만 잠갔으나, 판매자가 취소 공연에 적용된 기준을 볼 곳이 공연의 규정뿐이라 뒤에 고치면 화면이 틀어진다. 감수: 상태만 봐서 작성 중에 취소된 공연만 쓰는 규정도 잠김 → `published_at`이 생기면 "공개한 적 있음"으로(DB TODO). 버린 대안: `PUBLISHED`만, SLR-18에 수수료 추가, 규정에 잠금 시각 저장.
12. **취소 규정 수정(SLR-22) (2026-11-16)**: 이름·구간 전체 교체(모두 지우고 새로 넣음), 같은 값·자기 이름은 200. 순서: `101` → 내 규정 확인(기본 409 `102`, 없음·남의 것 404 `100`) → 사용 중 409 `103` → 이름 중복 409 `104`. 기본 규정은 잠그지 않음. 처음의 행 잠금(`PESSIMISTIC_WRITE`)은 2026-11-18에 분산락으로 바꿈(정책 18 ⑦). 버린 대안: 바뀐 구간만 고치기, 엔티티에 `editable` 필드.
13. **등급·구역 조회(SLR-08)와 `locked` (2026-11-17)**: **취소되지 않은 회차 중 하나라도** 판매 좌석이 있으면 `locked`(가격은 좌석 생성 때 복사되어 일부만 만든 상태에서 고치면 회차끼리 어긋남. 취소 회차는 더 안 팔리고 환불은 `booking_seat.price`라 세지 않음). SLR-09~11의 409도 같은 기준. 등급은 가격 높은 순, 구역은 공연장 `sortOrder`순, 취소 공연도 조회, 대표·담당자 모두, 404 `PERFORMANCE000`. 버린 대안: 취소 회차까지 세기, 모든 회차 생성 때만. 회차·요일별 가격 차등은 범위 밖.
14. **등급 추가(SLR-09) (2026-11-17, 등급명·색은 정책 16으로 바뀜)**: 가격 0~1,000만 원(임시, 0원 결제 처리는 미확정), 등급 개수 상한 없음(삭제 API 보류), 취소 공연 409 `002`(취소하면 `locked`가 풀려 이력의 등급명이 바뀔 수 있음), 중복 409 `302`. 순서: 400 → 404 → `002` → `302` → `locked` 409 `301`. **락 없음**: 락이 막는 문제(옛 가격 복사)는 수정에만 있음. 같은 등급 동시 추가는 UNIQUE(V13)가 막는다. 버린 대안: 분산락, 20개 상한.
15. **등급 수정(SLR-10) (2026-11-17)**: 전체 교체, 중복은 다른 등급과만 비교, 이 공연 것이 아닌 등급은 404 `300`. 순서: 400 → 404(락 밖) → 락 → `002` → `300` → `302` → `301`. 가격 수정과 좌석 생성이 겹치면 공연 상세와 다른 금액을 결제하므로 분산락 `performance:{공연 번호}`(대기 1초 `app.performance.lock-wait`, 실패 `COMMON004`) + 안에서 트랜잭션. 감수: 좌석 생성도 같은 락이어야 효과(SLR-14에서 적용). 버린 대안: 락 없음, 공연 행 비관적 락(DB TODO).
16. **등급명은 enum, 색은 서버에서 뺌 (2026-11-18)**: 색은 프론트가 정하기로 해 이름도 코드로 바꿨다(NOL 티켓 40개 공연에서 모은 12개): `VIP`, `R`, `S`, `A`, `B`, `C`, `OP`, `VIEW_LIMITED`, `ALL`(전석), `STANDING`, `VIP_STANDING`, `RESERVED`(지정석). 화면 이름·색·표시명은 프론트. 코드는 추가만(이름 변경·삭제 없음), 목록 밖 값 400. API 필드는 `name` 그대로. ① 한 공연에 같은 등급은 하나(409 `302`). ② 전석과 다른 등급이 구역에 함께 지정되면 409 `PERFORMANCE303`(SLR-04·10·11, 최종 상태로 판단, 만들어 두기만 한 등급은 허용). ③ 지정석과 R·S 혼용은 막지 않음. 감수: 목록에 없는 이름은 못 씀. 버린 대안: 4~5개만, 같은 등급 여러 개, 전석을 등급 기준으로 막기, 표시명 서버 제공. 다른 담당자 API 명세(PFM-02·03, BKG-01·05, 2부·4부)도 사용자 요청으로 함께 고침.

33. **판매자 보류석(SLR-30~33) (2026-11-27)**: 팀 문서에는 상태 `RESERVED`, `AVAILABLE ⇄ RESERVED`, "좌석 생성 뒤에만"만 있었고 API·시기·요청 단위·에러·락·로그·화면이 없었다. ① API 네 개(구역 요약, 구역 좌석, 지정, 해제). 판매자는 좌석 번호를 알 방법이 없었고 작성 중 공연도 봐야 함. 버린 대안: 구역 좌석만 추가(구역을 다 열어 봐야 위치를 앎), 예매자 조회 공개(작성 중을 못 보고 B님 캐시가 얽힘). ② **지정은 판매 오픈 전까지, 해제는 회차 시작 전까지**. 버린 대안: 공개 전에만(공개 뒤 추가 회차를 못 잡고 남은 초대석을 못 팜), 언제든(고르던 좌석이 판매 중에 사라짐). 감수: 오픈 뒤 생긴 협찬 요청은 못 받음. ③ **일정 미정 연기 회차는 원래 일시가 지났어도 시작하지 않은 것으로 봄**(구현 중 확정). 버린 대안: 400(확정해야 풀 수 있는데 확정하는 순간 판매가 열려 그 사이를 못 씀). ④ `seatIds`(최대 500, 임시) 또는 `zoneIds`(제한 없음) 중 하나. 아레나 구역은 수천 석일 수 있음. 버린 대안: 번호 상한만 크게, 상한 없음, 회차 전체 보류(일시 중지가 맞는 기능). ⑤ 바꿀 수 있는 좌석만 바꾸고 나머지는 `skipped`(지금 상태), 0개면 409. 버린 대안: 전부 거절. ⑥ 공연 락 + 상태 조건부 UPDATE, 좌석 락은 안 잡음(오픈 때 예매 점유와 Redis를 다툼). 바뀐 좌석은 "보류였는지"가 뒤집힌 것으로 판단(해제 중 점유 만료·예매 취소가 만드는 `AVAILABLE`을 세지 않게). ⑦ 대표·담당자. 감사 로그는 요청당 한 줄, 좌석은 이름까지(끝난 회차 좌석은 지울 수 있음), 구역은 바뀐 수만. ⑧ 화면 포함(PR 1개): 회차의 "보류석" 화면. `ArenaMap`은 좌석 경로·좌석 모양·구역 설명·범례를 바꿔 끼우게 하고 기본값은 예매자 화면 그대로. ⑨ 보류 용도·메모는 안 받음(컬럼 없음), 보류석으로 초대권 발권은 범위 밖. 마이그레이션·Redis 키·스레드 추가 없음.

- 공연장 사용 중지와 기존 회차(중지 기능을 만들 때 담당자와): 중지 확인은 등록·공연장 변경·회차 추가뿐이고 공개·수정·좌석 생성·점유·회차 수정·판매 재개는 허용한다(앱에 중지 기능이 없음). 정할 것: ① 새 회차만 막을지 전부 취소·환불할지 ② 두 방식의 구분 방법 ③ 회차 수정·재개를 막을지 ④ 점유를 막을지.

## 프론트 참고 (화면에서 챙길 것)

> 백엔드는 막지 않지만 판매자가 모르고 지나치면 곤란한 것을 적는다.

- **공연장 변경(SLR-03)**: 구역 설정과 판매 좌석(보류석 포함)이 초기화되므로 확인을 받는다.
- **수령 방법 변경(SLR-03)**: 배송으로 결제된 예매는 그대로라 계속 배송해야 한다고 안내.
- **취소 규정(SLR-19~22)**: 잠긴 규정은 "복사해서 새로 만들기"로 안내(`editable`로 미리 표시). 여러 공연이 쓰면 함께 바뀜. 수수료 경고는 취소 가능 구간끼리, 전부 취소 불가면 저장 전 경고. 응답은 `daysFrom` 큰 순, 목록은 20개 페이지(기본 규정은 첫 페이지).
- **등급 가격(SLR-09·10)**: 100만 원 초과는 강조하거나 재확인. 0원 결제 처리는 미정.
- **회차별 예매 목록(SLR-18)**: 취소 뒤 기본 목록이 비므로 "전체 취소 보기"(`status=CANCELED`) 제공. 금액은 수수료 없는 표값임을 이름에 드러냄. 현장 확인은 `bookingNo`.
- **좌석 생성·보류석(SLR-14, SLR-30~33)**: 보류석은 좌석 생성 뒤에만(화면은 2026-11-27 구현: 회차의 "보류석"). 직접 생성(회차마다, 생성 후 등급·가격·구역 잠금 → 확인 필요)과 자동 생성(공개 공연, 오픈 24시간 전부터 최대 1시간 지연, 작성 중은 안 됨, 실패 알림 없음)을 안내. 고칠 것은 가격 먼저, 구역 마지막. 생성 여부는 `seatsGeneratedAt`·`seatsGenerated`.
- **회차 추가(SLR-12)**: 공개 공연은 바로 보이므로 저장 전 확인, 오픈 24시간 안이면 좌석이 바로 생성돼 잠긴다고 알림. `405`는 판매 종료를 늘리게, `010`은 새 공연 등록으로 안내. 회차 취소 API는 아직 없음.
- **회차 수정(SLR-13)**: ① 결제 화면의 일시는 예매 상세의 `schedule.startAt`을 보여 줘야 한다(저장해 둔 값을 먼저 쓰는 문제, client 담당과). ② 판매자 수정 버튼은 저장 전 확인, 시작·연기·취소 회차는 숨김, `011`은 메시지 그대로, `408`은 판매 종료를 먼저 앞당기게.
- **이메일 인증(AUTH-17·18)**: 가입 화면 구현은 `components/email-verification.tsx`에 있다. 명세는 `api-spec.md` "가입 전 이메일 인증".
- **판매 일시 중지(SLR-26·27)**: 화면은 PR 158에서 구현. 명세는 `api-spec.md` SLR-26·27.
- **회차 연기(SLR-28·29)**: 화면 구현(2026-11-27). ① 판매자 상세: 회차 줄의 "연기"·"새 일정 확정" 버튼과 입력 창(거절 사유는 창 안에 표시), 확정 창에 "확정하면 바로 판매가 열립니다". `PERFORMANCE010`에 미정 회차가 있으면 "먼저 새 일정을 확정" 안내. ② 예매자 상세: 회차 아래 연기 안내(원래 일시·사유·무료 취소 마감, 새 일시는 회차 버튼의 값). ③ 좌석·대기열·결제·승인: `BOOKING013`은 중지와 같은 알림 창(`sale-paused-modal`에 제목 인자 추가). 승인에서 거절되면 "다시 결제하기"를 숨김. ④ 목록 "연기" 배지·"일정 미정", 내 예매의 일정 미정 표시와 무료 취소 마감. 남은 것: 날짜를 바꾼 연기 전에 만든 결제 대기 예매는 결제 화면에 예전 일시가 보이고 결제를 눌러야 알게 됨(화면이 알 값이 없음).
