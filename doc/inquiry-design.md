# 문의 설계

> 예매자·판매자가 문의를 쓰고 관리자가 답변한다. (2026-11-24, B)
> 작은 기능 단위 PR로 나눠 만든다. 이 문서의 표시: ✅ 구현됨 · ⏳ 다음 PR

## 1. 정한 것

| 항목 | 결정 |
|---|---|
| 테이블 | 예매자·판매자가 **한 테이블(`inquiry`)을 같이 쓴다.** 관리자는 한 목록에서 작성자 종류로 걸러 본다 |
| 답변 | 문의 하나에 관리자 답변 **하나**. 주고받기는 없고, 더 물을 것이 있으면 새 문의를 쓴다 |
| 상태 | `WAITING` 답변 대기 / `ANSWERED` 답변 완료, 둘만 |
| 수정·삭제 | 작성자가 **답변 전에만** 할 수 있다. 삭제는 소프트 삭제(`deleted_at`) |
| 예매 연결 | 예매자 문의는 내 예매를 **골라도 되고 안 골라도 된다.** 회원·가입 문의처럼 예매가 없는 문의가 있어서. 예매 상태는 따지지 않는다 |
| 첨부 사진 | 주소 문자열만 받는다. 사진은 이미지 업로드(IMG-01, `USER_INQUIRY`·`SELLER_INQUIRY`)로 먼저 올린다. 최대 3장(임시) |
| 이력 | 작성·수정·삭제·답변마다 그때 내용을 통째로 `inquiry_history`에 남긴다 |
| 답변 알림 | 없음. 목록의 상태로 확인한다. (나중에 추가 기능으로) |
| 문의 유형 | 예매자·판매자가 고를 수 있는 유형이 다르다. 아래 표, **값은 임시** |
| 길이 | 제목 100자, 내용 2,000자, 답변 2,000자 (임시, 컬럼 크기와 같음) |

### 문의 유형 (임시)

| 값 | 이름 | 예매자 | 판매자 |
|---|---|---|---|
| `BOOKING` | 예매 | ✅ | |
| `CANCEL_REFUND` | 취소·환불 | ✅ | |
| `PAYMENT` | 결제 | ✅ | |
| `DELIVERY` | 티켓 배송·수령 | ✅ | |
| `ACCOUNT` | 회원·계정 | ✅ | |
| `PERFORMANCE` | 공연 등록·수정 | | ✅ |
| `SETTLEMENT` | 정산 | | ✅ |
| `BUSINESS` | 사업체·계정 | | ✅ |
| `ETC` | 기타 | ✅ | ✅ |

- 화면은 유형 목록 API로 **내 계정이 고를 수 있는 것만** 받는다. 다른 유형을 보내면 작성 때 서버가 400(`INQUIRY000`)으로 막는다. (화면만 막으면 API를 직접 부르는 요청이 통과한다)

## 2. 테이블 (`V14__create_inquiry_tables.sql`)

```
inquiry (문의 1건 = 1행, 첨부 사진 주소는 image_urls 컬럼에 JSON 배열로)
  └─ 1:N inquiry_history (작성·수정·삭제·답변 기록)
```

### `inquiry`

| 컬럼 | 설명 | 예매자 | 판매자 |
|---|---|---|---|
| `author_type`, `author_id` | 작성자 종류(`USER`/`SELLER`)와 번호. **항상 같이 쓴다** | 필수 | 필수 |
| `business_id` | 사업체. 같은 사업체의 대표·담당자가 함께 본다 | 비움 | 필수 |
| `author_name`, `author_email` | 작성 때 복사한 이름·이메일 | 필수 | 필수 |
| `category` | 문의 유형 | 필수 | 필수 |
| `booking_id` | 고른 내 예매 | 선택 | 비움 |
| `title`, `content` | 제목, 내용 | 필수 | 필수 |
| `image_urls` | 첨부 사진 주소 목록 (jsonb 배열, 최대 3장, 없으면 `[]`) | 선택 | 선택 |
| `status` | `WAITING` / `ANSWERED` | 필수 | 필수 |
| `answer`, `answered_by`, `answered_at` | 답변, 답변한 관리자, 답변 일시 | 답변 후 | 답변 후 |
| `created_at`, `updated_at`, `deleted_at` | 시간, 소프트 삭제 | | |

- **작성자를 종류 + 번호로 가리키는 이유**: 예매자(`user_member`)와 판매자(`seller_member`)는 테이블이 달라 번호가 겹칠 수 있다. 번호만 조건에 넣으면 판매자 7번이 예매자 7번의 문의를 보게 된다. (대기열 키에 `USER:번호`를 붙인 것과 같은 이유)
- **이름·이메일을 복사하는 이유**: 작성자가 두 테이블에 나뉘어 있어 읽기 전용 연관 하나로 꺼낼 수 없다. 관리자 목록에서 작성자를 보여 주려고 쓸 때 복사한다. (예매가 주문자 정보를 복사하는 것과 같다)
- 판매자 문의는 다음 PR이지만, 컬럼을 다시 추가하는 마이그레이션을 만들지 않으려고 처음부터 만들었다.
- 인덱스: 내 문의 목록 `(author_type, author_id, created_at DESC)`, 사업체 목록 `(business_id, created_at DESC)`, 관리자 목록 `(status, created_at)`. 모두 삭제하지 않은 행만.

- **사진을 테이블로 나누지 않은 이유** (2026-11-24 변경: 처음에는 공연 상세 이미지처럼 `inquiry_image` 테이블이었다): 사진은 최대 3장이고, 늘 문의와 같이 읽고 쓰며, 수정할 때도 통째로 바꾼다. 사진 하나로 검색하거나 한 장만 고칠 일이 없다. 그래서 4부의 jsonb 기준("읽기만 하고 검색·부분 수정하지 않는 값", 취소 규정 스냅샷)과 같이 문의 행의 `jsonb` 배열로 둔다. 테이블·엔티티·저장 단계가 하나씩 줄고, 순서는 배열 순서 그대로다. 공연 상세 이미지는 개수 제한이 없고 공연 화면의 중심 데이터라 사정이 다르다.

### `inquiry_history`

| 컬럼 | 설명 |
|---|---|
| `inquiry_id` | 어느 문의의 기록인지 |
| `actor_type`, `actor_id` | 누가 (`USER` / `SELLER` / `ADMIN`) |
| `action` | `CREATED` / `UPDATED` / `DELETED` / `ANSWERED` |
| `title`, `content`, `image_urls`(jsonb), `answer` | 그 순간의 내용 그대로 |
| `created_at` | 언제 |

- 추가만 하고 고치거나 지우지 않는다.
- **왜 필요한가**: 답변 전 수정은 문의 본문을 덮어쓴다. 처음에 무엇을 썼는지, 삭제한 문의에 무엇이 있었는지, 관리자가 어떤 내용에 답했는지가 여기에만 남는다. 분쟁이 생겼을 때의 근거다.
- **감사 로그(`audit_log`)를 쓰지 않은 이유**: `audit_log`는 판매자·관리자·시스템의 행동만 남기는 공통 테이블(5부)이라 예매자 행동을 넣으려면 행위자 종류와 5부 원칙을 바꿔야 한다. 또 다른 도메인이라 문의를 저장할 때마다 파사드가 필요하다. 문의 이력은 문의 도메인 안에서 같은 트랜잭션으로 남기는 쪽이 단순해서 따로 뒀다.

## 3. 코드 구조

```
domain/inquiry
  controller/UserInquiryController   예매자 API (/api/v1/inquiries)
  facade/UserInquiryFacade           작성: 예매(내 예매인가) + 회원(이름·이메일) + 문의(저장)
  service/InquiryService             문의·이력 저장과 조회 (자기 도메인만)
  dto/UserInquiryRequest, UserInquiryResponse
  infra/entity/Inquiry, InquiryHistory
  type/InquiryStatus, InquiryCategory, InquiryAction
global/exception/code/InquiryExceptionCode
```

- 작성은 세 도메인을 읽고 써서 파사드가 순서대로 부른다. 목록·상세는 문의만 읽고, 예매 번호·공연 제목은 문의의 **읽기 전용 연관**(`Inquiry → Booking`)에서 꺼낸다.
- "내 것인가"는 작성자 종류 + 번호를 조회 조건에 넣어 거른다. 남의 문의는 403이 아니라 **404**다.
- 판매자·관리자 컨트롤러는 같은 도메인에 `SellerInquiryController`, 관리자는 팀 규칙대로 `domain/admin`에 둔다. ⏳

## 5. 알려진 한계

- **첨부 사진은 공개 주소다.** 이미지 업로드가 `public/` 아래에 올려서 주소를 아는 사람은 누구나 볼 수 있다. 화면에서 영수증·연락처 같은 개인정보가 담긴 사진을 올리지 않도록 안내한다. 비공개 경로 + 임시 주소(presigned URL)는 나중에.
- **반려된 판매자는 문의할 수 없다.** 로그인이 막혀 있어서다. 반려 이의는 문의가 아닌 다른 연락처로 받는다. (로그인 없는 문의는 범위가 커서 넣지 않았다)
- 탈퇴한 회원의 문의는 복사한 이름·이메일과 함께 남는다. 탈퇴 비식별 처리에 문의를 넣을지는 정하지 않았다.
- 올리고 문의에 등록하지 않은 사진은 버킷에 남는다. (이미지 업로드 전체의 한계와 같다)
