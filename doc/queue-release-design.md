# 대기열 자리 반납 개선 설계안 (설계안, 미구현)

대기열에 **입장한 사람의 자리를 언제 돌려줄지**를 정한다. 지금은 점유·결제를 끝내도 자리가 입장 유효 시간(10분)까지 남는다.
폴링 부담(상태 확인 간격 조정, 예상 대기 시간, 푸시)은 이 문서의 범위가 아니다. (8절) 기존 대기열 설계는 `doc/queue-design.md`다.

## 한눈에 보기

| 무엇을 | 어떻게 | 어디를 고치나 |
|---|---|---|
| ① 결제를 마친 사람 | **결제 완료 즉시** 자리 반납. 한도가 남아도 더 사려면 다시 줄을 선다 | 서버 (`PaymentFacade.confirm`) |
| ② 창을 닫거나 다른 사이트로 간 사람 | 브라우저가 닫히는 순간(`pagehide`) 바로 반납. **새로고침도 반납으로 본다(감수)** | 클라이언트 + 서버(변경 없음) |
| ③ ①②가 놓친 사람(모바일·강제 종료·가만히 있음) | 입장 유효 시간을 **10분 → 5분(임시)** 으로 줄이고, 구역·좌석·점유 요청이 올 때마다 연장(상한 20분) | 서버 (Lua·설정) |
| ④ 점유하고 튕긴 사람 | 결제 단계는 대기열 밖이라 **내 예매 → 결제 대기 → 결제**로 이어간다. **이미 된다.** 안내만 보강 | 클라이언트 (선택) |
| ⑤ 대기 화면 | "내 앞에 N명" 표시. 서버는 이미 순번·전체 인원을 준다 | 클라이언트 (작은 변경) |

- **마이그레이션·새 테이블·`SecurityConfig` 변경은 없다.** 설정값(`application.yaml`) 하나가 늘어난다.
- 효과는 한 회차에서 **새로 입장하는 속도 ≈ 정원 ÷ 평균 점유 시간**으로 본다. 정원 1,000에 평균 10분이면 분당 100명, 2분이면 분당 500명이다.

## 1. 왜 하나 (부하 시험 S1, 서버 1대, 3만 명 5분)

- 입장한 사람은 17,234명, 결제 완료는 4,783건(**약 28%**)이었다. 나머지 72%는 점유만 했거나 구경만 하고 떠났다.
- 시험(k6)은 흐름이 끝나면 `DELETE`로 자리를 돌려주게 되어 있다. **실제 사용자는 창을 닫고 떠나서 자리가 10분 동안 남는다.** 그래서 S1의 대기 시간(평균 21초, p95 33초)은 실제보다 짧다.
- 지금 자리가 비워지는 경우는 ① 입장 유효 시간(10분) 경과 ② `DELETE` 호출뿐이다. 클라이언트는 **줄을 선 채 떠날 때만** `DELETE`를 부르고, 이미 입장한 사람은 건드리지 않는다. 점유·결제 성공 때도 반납하지 않는다.

## 2. 결정과 버린 대안

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 결제 완료 즉시 반납 | 서버가 정확히 아는 사건이다. 매장에서 한 번 사면 다시 줄을 서는 것처럼 **한도가 남아도 다시 줄을 선다** | 한도를 채웠을 때만 반납(PR #151 방식): 더 여유롭고 복잡하다. 이 서비스는 그렇게 두지 않는다 |
| `pagehide`에서 즉시 반납 | 새로고침은 사용자의 실수로 보고 **자리를 잃는 것을 인정**한다. 구현이 단순하다 | 30초 유예 후 반납(새로고침을 구분): 서버 상태가 늘고 복잡해진다 |
| 짧은 입장 유효 시간 + 활동 시 연장 | 브라우저 신호가 안 오는 경우를 서버만으로 막는 안전망 | 신호에만 의존: 모바일·강제 종료에서 자리가 10분 남는다 |
| 연결을 계속 유지(SSE·웹소켓)해 떠남을 감지 | | 3만 명 연결 유지가 필요해 구조가 크게 바뀐다(과하다) |
| 점유 성공 즉시 반납 | | 점유한 사람이 좌석을 더 고르려면 다시 줄을 서야 한다. 결제 완료를 끝으로 본다 |

## 3. 자리가 비워지는 경우 (전과 후)

| 경우 | 지금 | 설계 후 |
|---|---|---|
| 결제 완료 | 안 됨 | **즉시** |
| 줄 선 채 화면을 닫음·떠남 | 클라이언트가 `DELETE` | 그대로 (`pagehide`로 더 확실히) |
| 입장 후 창을 닫음·다른 사이트로 감 | 10분 뒤 | **즉시** (`pagehide`) |
| 신호가 안 오는 경우 | 10분 뒤 | **마지막 활동 후 5분** (연장 상한 20분) |
| 점유만 하고 결제 안 함 | 10분 뒤 | 위와 같음 (점유 7분은 따로 만료) |

## 4. 설계 상세

### 4-1. 결제 완료 시 반납 (서버)

- `PaymentFacade.confirm`에서 결제 승인이 끝나 **DB에 커밋된 뒤에** `QueueService.leave(userId, scheduleId)`를 부른다. 회차 번호는 예매에서 얻는다. 파사드가 여러 도메인의 서비스를 엮는 자리라 규칙에 맞다.
- 반납이 **실패해도 결제는 그대로 성공**이다. 예외를 삼키고 `warn` 로그와 지표(`queue.release`의 `reason=payment`)만 남긴다. 어차피 입장 유효 시간이 안전망이다.
- 결제가 실패·취소되면 반납하지 않는다. 이미 끝난 승인을 다시 받는 경우(이중 승인)도 반납은 멱등이다. (`DELETE`는 줄에 없어도 성공)
- 락 안이나 트랜잭션 안에서 부르지 않는다. 외부 호출(토스)과 마찬가지로 Redis 호출도 DB 트랜잭션 밖에서 한다.

### 4-2. 창을 닫을 때 반납 (클라이언트)

- 좌석 화면(대기 중·입장 중)에서 `pagehide` 이벤트가 나면 `fetch(DELETE /api/v1/schedules/{id}/queue, { keepalive: true })`를 보낸다. 닫히는 중이라 일반 요청은 취소될 수 있어서 `keepalive`가 필요하다. (`sendBeacon`은 POST만 가능)
- 서버는 **기존 `DELETE`를 그대로 쓴다.** 본인 것만 지우고, 줄에 없어도 성공한다.
- 어떤 이동에서 신호가 나나:

| 상황 | `pagehide` | 결과 |
|---|---|---|
| 탭·창 닫기, 새로고침 | 발생 | 반납 (새로고침은 감수) |
| 다른 사이트로 이동 | 발생 | 반납. 어디로 갔는지는 알 수 없다 |
| 토스 결제창으로 전체 페이지 이동 | 발생 | 반납. 결제 단계는 대기열 밖이라 결제에는 지장이 없다. 결제 실패 뒤 좌석을 더 고르려면 다시 줄을 선다 |
| 우리 사이트 안 링크 이동(클라이언트 라우팅) | 발생 안 함 | 자리 유지. 좌석 화면에서 결제 화면으로 가도 그대로 |

- **뒤로 가기 복원**: 다른 사이트로 갔다가 뒤로 가면 브라우저가 화면을 그대로 복원할 수 있다(`pageshow`의 `persisted`). 자리는 이미 반납됐으므로 복원될 때 상태를 다시 확인해서 필요하면 재입장시킨다.
- 모바일은 앱 전환·강제 종료에서 신호가 안 올 수 있다. 그래서 4-3이 필요하다.

### 4-3. 입장 유효 시간 단축과 활동 시 연장 (서버)

- `app.queue.entry-ttl` 10m → **3m**(임시). 입장 확인(`queue-check.lua`, 구역 요약·구역 좌석·점유 요청마다)에서 입장자의 만료 시각을 `now + entry-ttl`로 **밀어 준다**. (지금은 읽기만 한다)
- 무한 연장을 막으려고 입장할 때 `admitted:USER:번호` 표시 키를 `entry-max`(**20m**, 임시) 만료로 만든다. 이 키가 있는 동안만 연장하고, 사라지면 연장하지 않아 자리가 `entry-ttl` 안에 비워진다.
- Redis 쓰기가 요청마다 늘지만 입장자(회차당 최대 1,000명)의 좌석 관련 요청에만 걸려서 부담은 작을 것으로 본다. 부담이 보이면 남은 시간이 `entry-ttl`의 절반 아래일 때만 연장한다.
- 값은 임시다. 5분이 좌석을 고르는 데 충분한지는 클라이언트 흐름과 부하 시험으로 정한다. 한 번 입장한 사람이 5분 동안 요청 없이 화면만 보고 있으면 자리를 잃는다.
- 새 설정 `entry-max`가 `QueueProperties`에 늘어난다. (설정 파일 `application.yaml`은 공용이라 팀에 알린다)

### 4-4. 점유하고 튕긴 사람 (이미 있음)

- 결제 준비·승인 API는 대기열을 거치지 않는다. 대기열은 구역·좌석·점유만 막는다.
- 클라이언트의 내 예매(`/bookings`)에 "결제 대기" 상태가 있고, 누르면 `/bookings/{id}/pay`로 이어진다. 점유 시간(7분) 안에 결제할 수 있다.
- 선택 보강(클라이언트): 점유 직후 "튕겨도 내 예매에서 이어서 결제할 수 있어요" 안내, 결제 대기 예매에 점유 남은 시간 표시, 재입장 화면에 "이 회차에 결제 대기 중인 예매가 있어요" 바로가기.

### 4-5. 대기 인원 표시 (클라이언트)

- 서버는 이미 `position`(내 순번, 1부터)과 `waitingCount`(전체 대기 인원)를 준다. 지금 화면은 "N번째"와 "전체 대기 M명"을 보여 준다.
- "내 앞에 **position − 1**명"을 같이 보여 준다. 서버 변경은 없다.
- 순번은 떠난 사람(유령 대기자)이 앞사람이 될 때까지 포함돼 실제보다 크게 보일 수 있다. 4-2가 이 현상을 줄인다. 예상 대기 시간은 이번 범위가 아니다.

## 6. 테스트 (돈·동시성 위주)

1. 결제 완료 → 그 사용자의 입장 자리가 비고 **대기 1순위가 입장**한다. (정원 경계, 동시 승인 여러 건에서 정원을 넘지 않음)
2. 결제 실패·취소 → 자리 유지. 이중 승인 → 반납이 한 번만 효과(멱등).
3. 반납 호출이 실패해도 결제는 성공으로 끝난다.
4. `DELETE`는 본인 것만 지우고, 줄에 없어도 성공한다. (기존 테스트 확인)
5. 활동 요청마다 만료가 연장되고, `entry-max`가 지나면 연장되지 않아 `entry-ttl` 뒤 자리가 빈다.
6. 클라이언트는 수동 확인: 창 닫기, 새로고침, 다른 사이트 이동 후 뒤로 가기, 토스 결제창 이동 후 복귀.

## 7. 부하 시험 계획

- 시험 스크립트(`a5_open.js`)의 자리 반납 방식을 바꿔서 같은 S1을 비교한다: 항상 반납(지금 시험) / 반납 없음 / 결제 완료 시 + 창 닫기 일부 비율 / 짧은 유효 시간만.
- 볼 것: 입장까지 평균·p95, 대기 포기율, 분당 입장 인원, 점유·결제 성공 수.

## 8. 범위 밖 (나중에)

- 상태 확인(폴링) 간격과 부담 줄이기(서버가 다음 확인 시점을 알려 주기), 예상 대기 시간, 푸시(SSE·웹소켓)
- 점유 요청 횟수 제한, 매크로 방어(`doc/later/queue-captcha-macro.md`)

## 9. 정해야 할 것

- `entry-ttl`(5m)과 `entry-max`(20m)의 값: 좌석 선택에 걸리는 실제 시간과 부하 시험으로.
- 결제 완료 반납을 `PaymentFacade`에 넣는 것에 대한 결제 담당과의 합의.
- 클라이언트 변경(`pagehide`, 내 앞에 N명)을 맡을 프론트 담당.
- 대기열 설계 문서(`doc/queue-design.md`)에 이 내용을 합칠 시점.
